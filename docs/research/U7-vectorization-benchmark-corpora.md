# U7 — Benchmark corpora and ground-truth extraction for a loop-vectorizing eval harness

**Date:** 2026-08-24
**Researcher:** research-agent
**Question:** What real-world "working but vectorizable" loop corpus should the OSIL
evaluation harness adopt, what does it cost (license), how do we extract a trustworthy
per-loop ground truth from the baseline compilers (clang/LLVM and GCC), what changes on
Apple Silicon (M4, NEON, no classic SVE), and what measurement protocol keeps the
resulting numbers honest under this project's non-negotiable evaluation philosophy
(correctness gates performance; held-out split; never score on what you optimized;
always report the losing lane)?

**Status relative to the repo:** feeds the (not-yet-built) evaluation harness for the
loop-vectorizing semantic optimizer. No gate currently depends on this file; treat it as
input to a future gate/ADR that adopts a corpus and a measurement protocol.

---

## TL;DR recommendation

**Adopt two corpora, not one, precisely because the project's philosophy requires a
held-out split that is *structurally* independent, not just a random subset of the same
generator:**

| Rank | Corpus | License | Role |
|---|---|---|---|
| 1 (primary) | **TSVC_2** (151 loops, C), run through the **`sergisiso/autovec-benchmark`** information-withholding harness pattern, *not* vanilla stock TSVC_2 | BSD-3-Clause (Polaris Research Group, UIUC) | Dev/tuning split — single-loop, SIMD-focused, wide pattern coverage (strides, indirection, reductions, control flow, recurrences) |
| 2 (secondary, held-out) | **PolyBench/C 4.2.1** (30 kernels) | OSU custom permissive license (BSD-like, non-endorsement clause) | Held-out generalization check — structurally different (multi-dimensional loop nests, polyhedral-shaped, has a *built-in* correctness-dump mode) from TSVC_2, so it cannot leak dev-split overfitting |

**Why two, and why these two:** TSVC_2 is the only corpus in this survey purpose-built
to *isolate* vectorization decisions one loop at a time — that is its essence, per the
original Callahan/Dongarra/Levine 1988 design. PolyBench is not primarily a vectorization
suite (it is a polyhedral loop-nest optimization suite — §2), but its kernels are real,
its correctness-dump mode (`POLYBENCH_DUMP_ARRAYS`) gives you an automated oracle TSVC_2
lacks, and — most importantly for this project's "never score on what you optimized"
rule — it is generated by a different design lineage than TSVC, so tuning
interpretation/rewrite rules against TSVC_2 and then measuring unchanged on PolyBench is
a real generalization test, not a leaderboard trick.

**The single highest-leverage methodology finding:** do **not** run stock TSVC_2 as
downloaded. Both TSVC_2's own README and a dedicated follow-on paper (Siso et al.,
TACO 2019, and its `autovec-benchmark` repo) document that when array sizes and trip
counts are compile-time constants, compilers (and by direct extension, any e-graph/rewrite-based
semantic optimizer working the same IR) can trivially constant-fold and fully unroll —
producing "vectorized" results that reflect constant-propagation, not vectorization
capability. This is the concrete, mechanical form of "never score on what you optimized"
for this domain. §7 gives the mitigation.

**Confidence:** HIGH on corpus existence/license/structure (primary-sourced, several
verified by direct download/build/run on the actual target machine — see §5–6). MEDIUM
on the "adopt two, not one" recommendation — that is a judgment call extrapolated from
the project's stated philosophy, not an external citation.

## 1. TSVC / TSVC_2

**Canonical location (verified):** [`github.com/UoB-HPC/TSVC_2`](https://github.com/UoB-HPC/TSVC_2)
— maintained by the University of Bristol HPC group. This supersedes the older C port
(`polaris.cs.uiuc.edu/~maleki1/TSVC.tar.gz`, Maleki et al. 2011) and the original Fortran
suite (`netlib.org/benchmark/vectord`, Callahan/Dongarra/Levine, *Vectorizing Compilers: A
Test Suite and Results*, Supercomputing '88). The old C port is also mirrored inside
`llvm/llvm-test-suite` at `MultiSource/Benchmarks/TSVC/` — that copy is the *older*,
pre-TSVC_2 version and inherits the bugs TSVC_2 fixed (see below); do not use it as the
primary source.

**Loop count:** **151 loop nests** — confirmed independently by (a) an aggregator list
of compiler benchmark suites (`quepas/Compiler-benchmark-suites`) and (b) a 2025 paper
that used TSVC_2 directly (arXiv:2502.11906, "Comparison of Vectorization Capabilities of
Different Compilers for X86 and ARM CPUs" — see §6). One loop nest per function, named by
convention (`s000`, `s111`, `s1111`, `s112`, …, plus a `v*` family for explicit vector
idioms like `va`, `vag`, `vpv`). Patterns cover linear dependence testing, strided/indirect
access, control flow (`if`/`goto` inside loops), reductions, recurrences, and interprocedural
cases — this breadth is TSVC's actual selling point over PolyBench.

**License (verified — fetched `license.txt` directly):** **BSD 3-Clause**, copyright the
Polaris Research Group, University of Illinois at Urbana-Champaign. Permissive: use,
modify, redistribute, sublicense at no cost; retains attribution/disclaimer requirements;
forbids using the Polaris/UIUC name for endorsement. Compatible with the repo's MIT
license (per ADR-0013) for a vendored corpus subdirectory with its own LICENSE file,
same pattern as any BSD-licensed conformance fixture.

**File/harness structure (verified — fetched `src/tsvc.c` and README directly):**
- `src/` — one `.c` file set implementing all kernels, dispatched through a
  `time_function()` driver in `main()`.
- `makefiles/` — per-compiler makefiles (gcc/clang/icc/cray/…), each producing **six**
  binaries: `tsvc_{vec,novec}_{relaxed,precise,default}` (vectorized vs. forced-scalar, ×
  three floating-point strictness modes).
- Correctness: **not automated pass/fail.** Each kernel returns/accumulates a checksum
  (`calc_checksum(__func__)` or a reduction value) that is fed to a `dummy()` sink (this
  is the anti-DCE mechanism — see below) and printed alongside the elapsed time:
  `printf("%10.3f\t%f\n", taken, result)`. There is **no shipped oracle that diffs this
  checksum against a known-good value** — you get a number per loop per run; establishing
  "is this correct" is left to the user (typically: compare checksums across the
  vec/novec/compiler variants and expect them to match within the FP tolerance implied by
  the `relaxed`/`precise` mode). **This is the harness's biggest gap for this project**:
  plan to add your own oracle layer (§8 gives the recommended approach — an independent
  `-O0`/`-fno-vectorize` reference build, not the compiler's own vectorized output).
- Timing: `gettimeofday()`-based, coarse (microsecond nominal resolution, but on modern
  hardware this is far coarser than a single loop's runtime unless `iterations` is scaled
  up — the harness does scale via a global `iterations` multiplier for exactly this
  reason).

**Known problems (verified from the README's own text and the follow-on literature):**
- *Original C port's DCE problem*: the TSVC_2 README states verbatim that the old C
  version "had some problems to do with compilers being able to inline all of the
  initialisation and checksum loops, which wildly skews the results and the timing" —
  this is precisely why TSVC_2 exists and why the `llvm-test-suite` mirror (which carries
  the old port) should be avoided as a source of truth.
- *No architecture-specific flags by default*: the README explicitly warns "none of the
  supplied makefiles have any architecture-specific flags and you will need to edit the
  makefiles to supply them" — on the M4 this means adding `-mcpu=apple-m4` (or
  `-march=armv8.7-a` / `-mcpu=native`) yourself; the stock makefiles will silently build
  generic ARM64 code with weaker vectorization if you don't.
- *Compile-time-constant leakage*: not called out in the stock README, but is the entire
  subject of §7's mitigation (`autovec-benchmark`) — array sizes/trip counts in the
  vanilla harness are `#define`d constants, which lets compilers over-perform relative to
  what they'd do on real, size-unknown-at-compile-time code.
- *Timing noise*: `gettimeofday` plus no documented warmup/repeat protocol in the stock
  harness — treat the shipped `time_function()` numbers as a starting point only; layer
  your own repeat/median protocol (§9) on top.

## 2. PolyBench/C 4.2.1

**Canonical location:** the original host, `web.cse.ohio-state.edu/~pouchet/software/polybench/`
(Louis-Noël Pouchet, Ohio State), now **redirects (HTTP 301) to a generic OSU CSE
directory page — the original page is dead.** Live replacements, both mirroring the
same 4.2.1 tarball: [`sourceforge.net/projects/polybench`](https://sourceforge.net/projects/polybench/)
(the SourceForge project is still the canonical *release* host — the aggregator list in
§1 links `polybench-c-4.2.tar.gz` directly from SourceForge) and the GitHub mirror
[`MatthiasJReisinger/PolyBenchC-4.2.1`](https://github.com/MatthiasJReisinger/PolyBenchC-4.2.1),
which is a faithful, unmodified copy of the tarball and is easier to vendor via a normal
git fetch than SourceForge's download flow.

**Kernel count:** **30 numerical kernels**, static control flow, spanning linear algebra
(BLAS-style: `gemm`, `gemver`, `symm`, `syrk`, `syr2k`, `trmm`, `trisolv`, `gramschmidt`,
`lu`, `ludcmp`, `cholesky`), stencils (`jacobi-1d`, `jacobi-2d`, `seidel-2d`, `heat-3d`,
`fdtd-2d`, `adi`), and datamining/misc (`correlation`, `covariance`, `2mm`, `3mm`,
`atax`, `bicg`, `doitgen`, `mvt`, `gesummv`, `durbin`, `floyd-warshall`, `nussinov`,
`deriche`). This is confirmed against the README of the GitHub mirror.

**License:** Ohio State's own custom permissive license (verified — fetched
`LICENSE.txt`): source/binary redistribution allowed with attribution + disclaimer
retained; forbids using OSU's name for endorsement; strong liability disclaimer;
"APPROVED FOR PUBLIC RELEASE, UNLIMITED DISTRIBUTION" (DARPA/DOE/NSF-funded). Functionally
BSD-like. Not SPDX-registered under a standard identifier — if the repo's `matrix-refresh`
or licensing-audit skill requires an SPDX tag, this one needs a custom entry, same
treatment as any other bespoke academic license already vendored under `conformance/`.

**Verification mode (verified from README):** `POLYBENCH_DUMP_ARRAYS` is a compile-time
macro that makes each kernel **dump all live-out arrays to stderr** at the end of the
run, in a fixed textual format. The intended workflow is: compile once with a trusted
(unoptimized or reference) configuration, capture the dump as a golden file, then
recompile with the optimization under test and diff the dumps. This is a real,
already-built correctness oracle — the thing TSVC_2 lacks — which is the concrete reason
to keep PolyBench in the corpus set even though it isn't primarily a vectorization suite.

**Is it appropriate for vectorization specifically?** **Not primarily — be honest about
this.** PolyBench's own framing (per its README and the wider polyhedral-compilation
literature it comes from, Pouchet's PoCC/PLuTo lineage) is loop-nest transformation:
tiling, fusion, interchange, skewing — i.e., polyhedral optimization for locality and
parallelism, of which auto-vectorization of the innermost loop is one *downstream*
consequence, not the design target. Many kernels are multi-dimensional nests where the
vectorizable unit is buried inside 2–4 levels of loop, versus TSVC_2's one-loop-per-kernel
isolation. Use PolyBench as the held-out *generalization* check (§ TL;DR), not as the
primary loop-vectorization corpus — mixing up these two roles would itself be a form of
"scoring on what you didn't actually optimize for."

## 3. LLVM test-suite — `SingleSource/UnitTests/Vectorizer`

**Location (verified):** [`github.com/llvm/llvm-test-suite`](https://github.com/llvm/llvm-test-suite),
path `SingleSource/UnitTests/Vectorizer/`. Contents (verified via directory fetch):
`gcc-loops.cpp` (the classic "loops GCC's vectorizer handles" regression set, adopted by
LLVM), `recurrences.cpp`, `runtime-checks.cpp`, `argmin-argmax-{int,fp}.cpp`,
`fmax-reduction.cpp`, `any-of.cpp`, `early-exit.cpp`, `find-last.cpp`, plus a
`VPlanNativePath/` subdirectory (tests specific to LLVM's VPlan-based outer-loop/native
vectorization path) and a `CMakeLists.txt`.

**License (verified — fetched `LICENSE.TXT`):** **Apache License 2.0 with LLVM
Exceptions** — the same license as LLVM/Clang itself. Fully compatible with the repo's
MIT license; this is the easiest of the three main corpora to vendor from a pure
licensing-friction standpoint.

**Build/run:** LLVM test-suite is CMake + `lit`-driven (LLVM's own test runner), typically
configured via `llvm-lit` against a `llvm-test-suite` checkout pointed at your `clang`.
This is heavier machinery than TSVC_2's flat makefiles — you're pulling in LLVM's full
test infrastructure to run what is, content-wise, a much smaller and narrower set of
loops than TSVC_2 (a few dozen files vs. 151 isolated kernels). **Recommendation: treat
this as a source of a handful of *additional, real-world-shaped* test cases to hand-pick
and vendor individually into the corpus** (e.g., `gcc-loops.cpp`'s named idioms are good
adversarial/regression cases — reductions, early-exit patterns LLVM only recently learned
to vectorize), not as a corpus to run wholesale via its own harness. Running it wholesale
duplicates TSVC_2's coverage while adding CMake/lit as a new build dependency for
comparatively little unique signal.

## 4. Other corpora

**Diospyros (`cucapra/diospyros`, ASPLOS 2021).** Verified: MIT license
(Copyright 2019 Cornell Capra). This is a synthesis-based vectorizing compiler for small,
fixed-size DSP linear-algebra kernels (2D convolution, matrix multiply, "q-prod", QR
decomposition — 21 total kernel *instances* once size variants are counted), targeting a
specific DSP's custom vector ISA (Tensilica Fusion G3), not general-purpose SIMD/NEON. Its
correctness methodology is genuinely interesting and directly transferable regardless of
target ISA: **translation validation** — the scalar spec and the synthesized vector code
are both lowered into an "imperative vector DSL" and checked for semantic equivalence,
printing `"Translation validation successful! N elements equal"` on success. Given this
project already has an egglog-based equivalence-preservation contract (ADR-0009, gate
G14), Diospyros's translation-validation framing is closer to OSIL's own philosophy than
either TSVC_2 or PolyBench's checksum/dump approaches — **worth reading as a design
reference for the harness's correctness gate**, even though its actual kernels are too
few and too DSP-specific to adopt as the corpus itself.

**ComPile (`llvm-ml/ComPile`, arXiv:2309.15432).** Verified: CC-BY-4.0, hosted on
HuggingFace, ~182B tokens of raw LLVM IR/bitcode mined from production package builds
(Rust, Swift, Julia, C/C++ via Spack/crates.io/etc.). **Does not contain loop-level
vectorization labels** — it is unlabeled IR, positioned as pretraining/statistical-analysis
material for ML-for-compilers work, not a benchmark-with-ground-truth. Not directly
usable for this project without a separate labeling pass (you'd have to run clang/GCC's
own vectorizer over subsets and mine the optimization-remarks YAML yourself — at which
point you're doing the §5/§6 work over arbitrary, uncurated code instead of over
already-curated, individually-isolated loops). **Not recommended as a first corpus**; flag
as a candidate *later* if the harness needs volume/diversity beyond TSVC_2 + PolyBench,
since the extraction machinery in §6 would carry over directly.

**Paired scalar/vectorized ground-truth work (direct hit on the "any recent dataset"
question, item 4):** **LLM-Vectorizer** (Taneja et al., CGO 2025 — `dl.acm.org/doi/10.1145/3696443.3708929`,
also on the CGO 2025 program page) is exactly this: scalar-to-vectorized C pairs with
measured 1.1×–9.4× speedups over ICC/GCC/Clang baselines, validated with **Alive2**
(bounded translation validation on LLVM IR) rather than checksums. I could not retrieve
the PDF directly (403 from ACM's paywall via WebFetch) so I cannot verify from the
primary source whether the underlying benchmark set (and any public repo/dataset) is
TSVC-derived, PolyBench-derived, or a novel corpus, nor confirm its license —
`ASSUMPTION:` flagging this until read directly; worth a follow-up fetch via `gh`/direct
PDF download if the project wants to pursue Alive2-style validation instead of (or in
addition to) checksum/dump validation, since Alive2 is a stronger correctness guarantee
than either TSVC_2's or PolyBench's approach and would fit the "correctness gates
performance" philosophy tightly. Also found but not deep-dived: **SimdBench**
(arXiv:2507.15224, 136 SIMD-intrinsic generation tasks) and **AutoVecCoder**
(arXiv:2605.17978) — both are LLM-code-generation benchmarks (pass@k on producing
intrinsic-using code from a prompt), a different problem shape than "does an
optimizer/rewrite-system correctly and profitably vectorize an existing scalar loop" —
**not a fit for this harness**, noted only to close out the search.

**Halide/TVM benchmark sets, "RodiniaS":** searched directly; **no evidence found** that
Halide's or TVM's benchmark/app suites are packaged as a standalone, vectorization-labeled
loop corpus independent of their own auto-scheduler frameworks (they're built to be run
*through* Halide's/TVM's own compilation pipeline, not as freestanding C loops against an
arbitrary baseline compiler — adopting them would mean adopting their DSLs/schedulers as
a dependency, which is a much bigger commitment than this eval harness needs). "RodiniaS"
specifically **could not be found** as a named public corpus in any source checked
(general Rodinia — Che et al. 2009, IISWC — is a *GPU* heterogeneous-computing suite,
23 CUDA applications; a "scalar/sequential CPU subset" variant may exist inside some
paper's artifact evaluation but I found no canonical, independently citable release under
that name). `ASSUMPTION:` treat "RodiniaS" as either a project-internal name from a
specific paper's artifact (possibly the withholding-information paper or the
vectorization-comparison paper in §6, worth asking whoever mentioned it rather than
guessing further) or a mishearing/conflation — not worth chasing further without a
firmer lead.

## 5. Ground truth from clang/LLVM — verified against the actual local toolchain

This machine (the M4 target itself) has **Apple clang 17.0.0** (`clang-1700.6.3.2`,
Xcode 26.2, `arm64-apple-darwin25.5.0`). Rather than trust generic docs, I compiled two
real test loops (a clean SAXPY and a branchy select-shaped loop) and captured actual
output — this is stronger evidence than the docs pages alone, per this project's evidence
hierarchy (empirical > documentation-as-described, when they might diverge on a
vendor-forked compiler like Apple's).

**Remark flags — confirmed working, exact current syntax:**
```
clang -O3 -mcpu=apple-m4 \
  -Rpass=loop-vectorize -Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize \
  -c loop.c -o loop.o
```
Actual output produced:
```
vec_test.c:2:5: remark: vectorized loop (vectorization width: 4, interleaved count: 4) [-Rpass=loop-vectorize]
vec_test.c:8:5: remark: vectorized loop (vectorization width: 4, interleaved count: 4) [-Rpass=loop-vectorize]
```
`-Rpass=` matches successful transforms by the named pass (regex over pass name);
`-Rpass-missed=` reports attempted-but-failed; `-Rpass-analysis=` reports the specific
blocking reason (e.g., in a genuinely non-vectorizable case, LLVM's docs give the pattern
`loop not vectorized: loop contains a switch statement` — I did not reproduce a missed
case locally in this quick test since both sample loops happened to vectorize, including
the branchy one via if-conversion; this sub-claim is doc-sourced, not independently
reproduced here). Add `-gline-tables-only -gcolumn-info` for accurate file:line:column
attribution per LLVM's own vectorizer docs.

**Structured optimization record — confirmed working, exact schema observed:**
```
clang -O3 -mcpu=apple-m4 -fsave-optimization-record \
  -foptimization-record-file=out.opt.yaml -c loop.c -o loop.o
```
Real YAML emitted (excerpted):
```yaml
--- !Passed
Pass:            loop-vectorize
Name:            Vectorized
DebugLoc:        { File: vec_test.c, Line: 2, Column: 5 }
Function:        saxpy
Args:
  - String:          'vectorized '
  - String:          'loop (vectorization width: '
  - VectorizationFactor: '4'
  - String:          ', interleaved count: '
  - InterleaveCount: '4'
...
--- !Missed
Pass:            slp-vectorizer
Name:            NotBeneficial
DebugLoc:        { File: vec_test.c, Line: 8, Column: 5 }
Function:        sum_with_branch
Args:
  - String:          'List vectorization was possible but not beneficial with cost '
  - Cost:            '0'
  - String:          ' >= '
  - Treshold:        '0'
...
```
Confirmed schema fields: `--- !{Passed|Missed|Analysis|...}` document type, `Pass`,
`Name` (a stable-ish remark identifier, e.g. `Vectorized`, `NotBeneficial`), `DebugLoc`
(`File`/`Line`/`Column` — this **does** give loop location), `Function`, and a
free-text-plus-typed-key `Args` list whose keys vary by remark (`VectorizationFactor`,
`InterleaveCount`, `Cost`, `Treshold` [sic — this is LLVM's actual, misspelled key, not a
transcription error]). This matches LLVM's own `docs/Remarks.html` schema description
(Type/Pass/Name/Function + optional DebugLoc/Hotness/Args). **This is the recipe to use
for automated, machine-parseable per-loop ground truth** — parse the YAML directly (it's
flat and regular) rather than scraping `-Rpass` stdout text.

**Gap found empirically, worth flagging:** `llvm-opt-report` (the tool LLVM ships to
turn this YAML into a human-readable annotated-source report, e.g. `8 V4,1 | for (...)`)
is **not bundled with Apple's Xcode toolchain** — confirmed via `which`/`xcrun --find`,
both failed. `brew install llvm` (Homebrew's stock LLVM, currently 22.1.8 per this
machine's `brew info llvm`) does ship it, but that's a second, separate LLVM toolchain
from Apple's — if you want `llvm-opt-report`'s human-readable view you need to either
install Homebrew LLVM alongside Apple clang or write your own ~50-line YAML parser
against the schema above (recommended: the schema is simple enough that a purpose-built
parser is less fragile than depending on a second full LLVM install just for reporting).

**GCC's equivalent — also verified empirically on this machine** (Homebrew GCC 16.1.0,
`gcc-16`, since macOS's `/usr/bin/gcc` is actually Apple clang aliased, confirmed by
identical `--version` output):
```
gcc-16 -O3 -mcpu=apple-m4 -fopt-info-vec-all -c loop.c -o loop.o
```
Real output:
```
vec_test.c:2:23: optimized: loop vectorized using 16 byte vectors and unroll factor 4
vec_test.c:1:6: note: vectorized 1 loops in function.
vec_test.c:5:1: note: ***** Analysis failed with vector mode V4SF
vec_test.c:5:1: note: ***** Skipping vector mode V16QI, which would repeat the analysis for V4SF
vec_test.c:8:23: missed: couldn't vectorize loop
vec_test.c:8:23: missed: not vectorized: unsupported control flow in loop.
vec_test.c:7:6: note: vectorized 0 loops in function.
```
Flag reference (cross-checked against `gcc.gnu.org/onlinedocs/gcc/Developer-Options.html`,
current docs): `-fopt-info` takes a comma-free concatenation of a *message-type* keyword
(`optimized` | `missed` | `note` | `all`) and an *optimization-group* keyword (`vec` |
`loop` | `inline` | `ipa` | `omp` | `optall`), e.g. `-fopt-info-vec-optimized`,
`-fopt-info-vec-missed`, `-fopt-info-vec-all` (both types combined), `-fopt-info-vec-note`
(internal detail, as seen in the `V4SF`/`V16QI` analysis lines above). Default report
level (bare `-fopt-info`) is `optimized-optall`. GCC's format is
`file:line:col: {optimized|missed|note}: <message>` — line/column granularity like
clang's, but plain text on stderr, no structured YAML/bitstream sibling to
`-fsave-optimization-record` (GCC does have `-fdump-*` and `-fopt-info=<file>` to redirect
to a file, but the payload stays free-text, not machine-schema'd).

**Concrete cross-compiler divergence found in this same 2-loop test — directly relevant
to "report the lane where you lose":** GCC 16 **refused to vectorize** the branchy loop
(`"not vectorized: unsupported control flow in loop"`), while Apple clang 17
**vectorized it** (both loops got the same `vectorization width: 4, interleaved count: 4`
remark). Same source, same target (`-mcpu=apple-m4`), same optimization level, different
vectorizers, different outcomes. This is exactly the kind of loop a semantic
optimizer needs a policy for: is "the loop GCC gives up on" a target lane where OSIL is
expected to *beat* GCC's ground truth (legitimate win), or a lane where instability
between baseline compilers means the "ground truth" itself is compiler-dependent and any
comparison needs to name which baseline it's measured against? **Recommendation for the
harness: always report per-loop results against *both* baseline compilers separately,
never a single merged "the baseline" number** — this single test case is proof the two
baselines already disagree on non-exotic C.

## 6. Apple Silicon / ARM caveat — verified on the actual M4 target

**Confirmed directly on this machine** (`sysctl`, `machdep.cpu.brand_string`, and
clang's own predefined-macro dump with `-march=native`):

- `machdep.cpu.brand_string: Apple M4` — base M4 (not Pro/Max): **4 performance cores +
  6 efficiency cores** (`hw.perflevel0.physicalcpu: 4`, `hw.perflevel1.physicalcpu: 6`).
  L1D: 128KB (P-core) / 64KB (E-core). L2: 16MB (P-cluster) / 4MB (E-cluster). Cache line:
  **128 bytes** (double the common x86 64-byte assumption — matters for false-sharing and
  prefetch-distance reasoning in the measurement protocol, §9).
- `hw.optional.neon: 1`, `hw.optional.arm.AdvSIMD: 1` — **NEON (AdvSIMD) confirmed
  present**, 128-bit vector registers, as expected.
- `hw.optional.arm.FEAT_SVE_B16B16: 0` and **no plain `FEAT_SVE` key present at all** in
  `sysctl -a` output. Compiling with `clang -march=native -dM -E -x c /dev/null` and
  grepping predefined macros shows `__ARM_NEON`, `__ARM_NEON_FP`, `__ARM_NEON__`,
  `__aarch64__` — **`__ARM_FEATURE_SVE` is not defined**, confirming Apple clang does
  **not** target classic SVE for this hardware even at `-march=native`.
- `hw.optional.arm.FEAT_SME: 1`, `hw.optional.arm.FEAT_SME2: 1` — SME/SME2 (Scalable
  Matrix Extension) **are** present. This matches the external research finding (Phoronix
  LLVM-commit coverage, and the `tzakharko/m4-sme-exploration` writeup found in search):
  M4 implements ARMv9.2-A's SME/SME2 coprocessor path (successor to Apple's proprietary
  AMX, now standard ARM ISA) but SVE proper is exposed **only inside SME's "streaming
  mode"**, not as a general-purpose vector-length-agnostic instruction set available to
  ordinary compiled code the way it is on server-class ARM (Neoverse, Graviton).
  `ASSUMPTION` (external, not independently re-verified beyond the empirical macro check
  above): outside of a deliberately-entered streaming-SVE region, issuing an SVE
  instruction on M4 traps (`EXC_BAD_INSTRUCTION`) — consistent with plain SVE simply not
  being advertised to the normal compilation target.
- **Practical consequence for this project: NEON (128-bit, `-mcpu=apple-m4` or
  `-march=armv8.7-a`/`-march=armv9.2-a` without an explicit `+sve`) is the only vector ISA
  the loop-vectorizing optimizer should target on this machine for ordinary loop bodies.**
  SME2 is real and present but is a matrix/streaming-mode facility (think: BLAS-style
  GEMM acceleration, not general elementwise loop vectorization) — out of scope for a
  general loop-vectorization benchmark unless the corpus specifically includes
  matrix-multiply-shaped kernels the optimizer intends to lower to SME (PolyBench's
  `gemm`/`2mm`/`3mm` would be the natural candidates if that's ever pursued, but that's a
  distinct, harder target than NEON loop vectorization and should be its own gate).

**Realistic speedup ceilings, NEON vs. the x86 numbers most papers quote:** raw SIMD
width gives the naive ceiling — NEON's 128-bit register holds 4×f32 or 2×f64, vs. AVX2's
256-bit (8×f32/4×f64) or AVX-512's 512-bit (16×f32/8×f64). **Do not extrapolate "NEON
therefore gets 1/2 or 1/4 of the AVX numbers in a paper"** — two independent, verified
findings push against a naive width-ratio extrapolation:
1. **Per-cycle issue width compensates.** A widely-cited comparison (yiningkarlli.com,
   NEON-vs-SSE writeup) notes Apple's Firestorm (M1-generation, same lineage as M4's
   P-core) can issue **4 NEON instructions per cycle**, meaning aggregate throughput lands
   "in a similar place" to naive AVX-512 width expectations for many kernels, despite the
   4× register-width gap — this is a microarchitectural fact about Apple's core, not a
   general ARM property, and doesn't hold for lower-end ARM cores.
2. **Empirically, the compilers disagree on what to even try.** The 2025 paper
   (arXiv:2502.11906, §6 methodology below) found ARM-side vectorization *rates* (54–56%
   of TSVC_2's 151 loops) were actually **slightly higher** than x86 (46–54%) across
   GCC/Clang/ARM-vendor-compiler(ACFL), and reports cases (loop `s4115`, indirect
   gather-shaped access) where GCC/ACFL used SVE-class gather instructions effectively on
   ARM while x86 compilers struggled with the same pattern, and other cases where Clang
   chose 8×-unroll over vectorization on ARM and still matched vectorized performance.
   **Their explicit conclusion: "We cannot definitively say if any one compiler is
   significantly better than the others at vectorizing code on any given platform"** —
   and critically, **"the vectorized code did not always outperform the unvectorized
   code"** even when the vectorizer remark said success. Both quotes are load-bearing for
   this project's philosophy: they are direct, primary-sourced evidence that "the
   compiler vectorized it" (a §5 remark) and "it's faster" (a §9 measurement) are
   different claims that must both be checked, never inferred from each other.

**Do any of the surveyed suites break or mislead on ARM?** No outright breakage found,
but caveats:
- **TSVC_2**: as noted in §1, its makefiles ship with *zero* architecture flags by
  default — on ARM this is not "broken" so much as silently suboptimal (generic-target
  codegen) unless you add `-mcpu=apple-m4` yourself. This is the same problem on x86 too
  (no `-march=native` by default); it's a "you must configure this" gap, not an
  ARM-specific bug.
- **PolyBench**: platform-neutral (pure C, no intrinsics in the reference kernels),
  no ARM-specific issue found.
- **LLVM test-suite Vectorizer tests**: designed and primarily exercised against x86 in
  most published LLVM vectorizer work, but the tests themselves are portable C/C++; no
  x86-only intrinsics observed in the files listed in §3. Low risk.
- The **2025 x86-vs-ARM paper itself is the strongest available evidence** that TSVC_2
  specifically is *appropriate* for cross-architecture (including ARM/NEON) vectorization
  comparison — it is, after all, primary evidence of someone having already done exactly
  this comparison successfully on real ARM hardware with this exact corpus.

## 7. Benchmark methodology hazards

**Dead code elimination (DCE).** The single most-cited failure mode across every source
consulted (TSVC_2's own README, the `abseil` performance-tips post, the
`studyplan.dev`/Google Benchmark writeup). If the compiler can prove a loop's output is
never observed, it deletes the loop — you then "benchmark" an empty function and
conclude the optimizer is infinitely fast. **Mitigation, in order of robustness:** (a)
feed every result through a genuine data dependency the compiler cannot see through
(TSVC_2's `dummy()`-sink pattern, or Google Benchmark's `DoNotOptimize`/`ClobberMemory`
equivalents on other toolchains); (b) never rely on "checksum happens to get printed" as
your only anti-DCE mechanism — printf's own side effect is sometimes enough to block DCE
but is not guaranteed across all optimization levels and LTO configurations; (c) verify
by disassembly spot-check, not just by trusting the benchmark ran without crashing.

**Compile-time-constant leakage (the TSVC-specific version of "never score on what you
optimized").** Covered in §1/§ TL;DR — if loop trip counts, array sizes, alignment, or
non-aliasing are compiler-visible constants, the vectorizer (or a semantic-rewrite
optimizer working the same IR) can fully unroll/constant-fold instead of genuinely
vectorizing a general loop, inflating both the "vectorized!" rate and the measured
speedup relative to what real, size-unknown production code would see. **Direct
mitigation: `sergisiso/autovec-benchmark`** (a fork/extension of TSVC, ACM TACO 2019,
"Evaluating Auto-Vectorizing Compilers through Objective Withdrawal of Useful
Information") implements exactly this control as a set of preprocessor toggles —
independently choosing whether loop bounds, array offsets, conditional parameters, and
alignment/aliasing hints are visible at compile time or deferred to runtime — plus six
additional micro-kernels (binomial/Black-Scholes options pricing, Mandelbrot, convolution,
small matmul, stencil). Its `license.txt` documents provenance from both `llvm-test-suite`
and Intel ISPC's examples for those extra kernels — check each kernel's individual
attribution before vendoring. **Recommendation: run the harness with runtime-provided
(argv/`malloc`-sized, non-`restrict`-unless-explicitly-testing-that-variable) sizes as the
default mode**, using the compile-time-constant mode only as a deliberate, separately
labeled "best case" comparison lane — never mix the two into one aggregate number.

**Cold cache vs. warm cache.** Not deeply sourced in this pass beyond general knowledge
and the abseil/Google-Benchmark material — `ASSUMPTION:` standard practice (warmup
iterations before the timed region, working-set sized to fit intentionally inside vs.
outside a cache level depending on what you're trying to measure) applies here
unmodified; the M4's actual cache sizes (confirmed in §6: 128KB/64KB L1D, 16MB/4MB L2)
are the concrete numbers to size TSVC_2/PolyBench working sets against if you want to
deliberately place a lane in "fits in L1" vs. "exceeds L2" territory.

**Memory-bound vs. compute-bound loops — where SIMD gives ~nothing.** Directly evidenced:
one search result (studyplan.dev/Google-Benchmark writeup on SIMD) states plainly that
wider SIMD "stresses memory bandwidth more, which results in waiting more on Dcache
stalls, making queries more Dcache-stalls-bound than Execution-stalls-bound" — i.e., a
simple streaming copy/add loop (TSVC_2's `s000`-family and similar "vector add" kernels
are exactly this shape) is bandwidth-bound; going from scalar to 4-wide NEON does not
4× the throughput because the bottleneck was never the ALU. **This is the natural,
built-in "lane where you lose" the project's philosophy requires you to report**: pick at
least one bandwidth-bound streaming kernel (large-array elementwise add/copy, working set
several times L2) and report its (small, possibly negative after overhead) speedup
honestly alongside the compute-bound wins, rather than only reporting kernels chosen
because they vectorize well.

**Turbo/thermal variance on a laptop-class SoC.** Not independently re-verified against
Apple-specific thermal documentation in this pass — general knowledge plus this project's
own hardware (§6: M4, 4P+6E, fanless/thin-chassis-class laptop thermal envelope in a
16GB config) makes this a real risk: sustained loop-heavy benchmarking can trigger
frequency scaling mid-run, and unlike a data-center benchmark you have no "reserved,
isolated, pinned-frequency node" available by default on macOS. **Standard mitigations**
(cross-checked against general HPC-benchmarking practice, not a single primary source):
run each measurement multiple times interleaved (not "all of A, then all of B" — thermal
drift then correlates with treatment) with the measurement order randomized or at minimum
A/B/A/B alternated; discard/flag the first N iterations after any idle gap; report
median and a spread statistic (IQR or stdev), not a single number; consider `caffeinate`
to prevent macOS App Nap/sleep interference during long runs; be aware there is no
public/scriptable P-core-pin or fixed-frequency mode on Apple Silicon macOS the way
`cpupower`/`taskset` give you on Linux — `ASSUMPTION:` you can request scheduling
affinity hints via `thread_policy_set`/QoS classes to bias onto P-cores, but cannot force
a fixed clock; treat any single run's absolute number as noisy and lean on the
repeat/median protocol instead.

## 8. Recommended baseline-extraction recipe (verified, ready to script)

For each loop in the corpus, build twice and diff:

1. **Correctness oracle build** — a vectorizer-independent reference: 
   `clang -O0 -c loop.c` **or** `clang -O2 -fno-vectorize -fno-slp-vectorize -c loop.c`
   (both disable the loop/SLP vectorizers specifically while keeping other optimizations
   roughly comparable; `-O0` is the more conservative, harder-to-argue-with oracle but is
   slower to run and may change other semantics like inlining that affect timing-adjacent
   behavior, not correctness). Capture output via PolyBench-style array dump or a TSVC-style
   checksum computed identically across all builds.
2. **Baseline-compiler vectorized build(s)** — run **both** compilers, not one:
   ```
   clang -O3 -mcpu=apple-m4 -fsave-optimization-record \
     -foptimization-record-file=<loop>.clang.yaml -Rpass=loop-vectorize \
     -Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize -c loop.c
   gcc-16 -O3 -mcpu=apple-m4 -fopt-info-vec-all=<loop>.gcc.txt -c loop.c
   ```
   Parse `<loop>.clang.yaml` (flat YAML, schema in §5) and `<loop>.gcc.txt` (line-oriented
   `file:line:col: {optimized|missed|note}: message` text, format in §5) into a common
   per-loop record: `{loop_id, compiler, vectorized: bool, reason_if_missed: str,
   vector_width: int|null, source_loc: (file,line,col)}`.
3. **Diff step (correctness gate)** — compare the oracle's output dump/checksum against
   each vectorized build's output. Any mismatch beyond documented FP-reordering tolerance
   (TSVC_2's `relaxed`/`precise` distinction is the right vocabulary here) is a hard fail
   — per this project's "correctness gates performance" rule, a loop that fails this step
   is excluded from the performance table entirely, not just penalized in a score.
4. **Timing step** — only for loops that passed step 3 — per the protocol in §9.
5. Store all four artifacts (oracle output, both compilers' remark records, timing
   samples) per loop, so a fresh agent/reviewer can reconstruct any reported number
   without re-running the harness.

## 9. Measurement protocol (designed to survive review)

1. **Split first, tune second.** Partition TSVC_2's 151 loops into a dev subset (used
   while iterating on the optimizer/rewrite rules) and a held-out subset (touched only
   for final reporting) — a fixed, seeded, documented split, not "whatever happened to be
   convenient." Treat all of PolyBench/C as a second, structurally-independent held-out
   set (§ TL;DR) regardless of the TSVC_2 split.
2. **Both compile-time-constant and runtime-size lanes, kept separate** (§7) — report
   both, never blend.
3. **Both baseline compilers, kept separate** (§5's GCC-vs-clang divergence finding) —
   report "vs. clang -O3" and "vs. GCC -O3" as distinct columns, not one merged
   "vs. baseline."
4. **Correctness gate before any timing number is reported** (§8 step 3) — a loop with a
   correctness failure appears in the report as a failure, never silently dropped and
   never given a performance number.
5. **Repeat and report spread, not a point estimate.** Minimum: N ≥ 10 timed repetitions
   per loop per configuration, interleaved across configurations (not blocked) to spread
   thermal drift evenly (§7); report median and IQR (or min + stdev) per loop; flag any
   loop whose spread exceeds a set threshold (e.g., IQR > 10% of median) as noisy rather
   than trusting its point estimate.
6. **Explicitly include and report at least one memory-bound / "SIMD gives ~nothing"
   lane** (§7) — this is the mechanical implementation of "always report the lane where
   you lose."
7. **Pin what you can, disclose what you can't.** Disclose in the report: machine (M4,
   4P+6E, this exact `sysctl` fingerprint from §6), OS/toolchain versions (Xcode 26.2 /
   Apple clang 17.0.0 / Homebrew GCC 16.1.0, as verified in §5), and the acknowledged gap
   that macOS gives no fixed-frequency/isolated-core guarantee (§7) — do not claim
   lab-grade isolation you don't have; the honest move per this project's ethics is to
   name the noise source, not paper over it with more decimal places.
8. **Version and archive the corpus itself.** Vendor TSVC_2 and PolyBench/C at pinned
   commits/tarball hashes under the corpus directory (matching this repo's existing
   `conformance/` provenance-header convention, per `CLAUDE.md` rule 4) — a "held-out
   split" is not meaningful if the corpus can silently drift between the dev-tuning run
   and the reported run.

## What would make the resulting numbers dishonest (design against this)

- **Reporting "compiler said vectorized" as if it meant "measured faster."** §6's own
  primary source states plainly that vectorized code did not always outperform scalar
  code on the exact corpus this project should adopt. A remark (§5) is a claim about what
  the compiler *attempted*, not a performance result — keep these as two separate
  columns, always.
- **Letting compile-time-constant loop bounds/array sizes inflate the vectorization
  rate or speedup** (§7) — the single most concrete, sourced dishonesty risk found in
  this research, with a named, ready-to-adopt mitigation (`autovec-benchmark`'s
  withholding toggles).
- **Merging GCC's and clang's baselines into one number** — §5 shows they disagree on
  real, non-exotic loops on this exact hardware; a merged "beats the baseline" claim
  hides which baseline, and by how much, silently picking whichever one is more
  favorable.
- **Dropping correctness failures from the report instead of showing them as failures**
  — directly against this project's "correctness gates performance" rule; a corpus
  subset quietly excluded because it failed is functionally an undisclosed cherry-pick.
- **Reporting only compute-bound, cleanly-vectorizing kernels** and omitting the
  memory-bound lane (§7, §9.6) — curates away the project's own required "lane where you
  lose" disclosure.
- **A single timed run per configuration**, or a point estimate with no spread reported
  (§9.5) — on a thermally-variable laptop SoC with no fixed-frequency guarantee (§7),
  this converts ordinary run-to-run noise into an uncontested-looking headline number.
- **Tuning and measuring on the same TSVC_2 subset** — violates "never score on what you
  optimized" directly; the whole reason to add PolyBench as a structurally different
  held-out set (§ TL;DR) is that a random split of TSVC_2 alone would still let
  rewrite-rule engineering implicitly overfit to TSVC_2's specific idiom vocabulary.
