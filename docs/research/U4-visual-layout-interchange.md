# Research U4: Visual/Diagram Layout as a Normative, Interchangeable, Machine-Checkable Language Artifact

**Date:** 2026-08-12
**Researcher:** research-agent
**Question:** What does prior art teach about making diagram/visual layout a normative, interchangeable, machine-checkable part of a language spec — and what should that teach OAAS's `spec/visual.md` and its golden-render conformance loop?

**Feeds:** `docs/intake/synthesis-repo-organization.md` unknown U4. Directly informs `spec/visual.md` (not yet written) and unblocks the `render-verify` skill (`improvable/render-verify/SKILL.md`), which is currently a stub explicitly waiting on this research ("structural/SVG diff preferred over pixel diff — pending research U4's recommendation").

## Research method (wave decomposition)

Default line: "look up BPMN DI." Simulated finding: a spec sub-document with a coordinate schema. Findings below are organized by source; the TL;DR synthesizes across all six lines.

## TL;DR

**What OAAS's layout schema must contain (converging across every format studied):**

1. **Per-node geometry**, keyed by a stable reference to the semantic element's ID (not by document position) — `(x, y, width, height)` at minimum. Every format that treats layout as data does this: BPMN DI's `dc:Bounds`, Structurizr's `workspace.json`, Excalidraw's element `x/y/width/height`, Graphviz's `pos` (in `neato`/`fdp` input mode).
2. **Per-edge waypoints** as an ordered point list, not a derived/recomputed spline — BPMN DI's `waypoint` list on `BPMNEdge`, Excalidraw's arrow `points`, Graphviz's `pos` on edges (control points, `neato -n` only).
3. **Labels as independently-positioned sub-objects**, not implicitly placed relative to their owner — BPMN DI gives `BPMNLabel` its own `dc:Bounds`, separate from the shape/edge it annotates. This is the single most-overlooked field in ad hoc schemas; get it wrong and label collisions become unfixable without a full re-layout.
4. **Explicit collapse/expand state** for any container/composite node — BPMN DI's `isExpanded` boolean on `BPMNShape` is a direct, verified precedent.
5. **Explicit ordering (z-order)**, as its own field, not implied by array/document order — Excalidraw's `index` (fractional-indexing key) is the strongest precedent; array-order-as-z-order (also valid, and what SVG's painter's algorithm gives you for free) is the simpler fallback but breaks under concurrent/collaborative edits, which matters if OAAS is ever agent-co-edited.
6. **Viewport (scroll/zoom/pan)** — only Excalidraw persists this (`appState.scrollX/scrollY/zoom`), and it should be treated as **non-normative session state**, not part of the identity-preservation contract: it affects what a human sees on open, not what the diagram *is*. Recommend OAAS store it if present but exclude it from the golden-render diff.

**Recommended golden-render strategy: structural diff on the layout-as-data model, first; SVG/DOM structural diff, second; pixel diff, never as a gate.** This confirms the direction already stubbed in `improvable/render-verify/SKILL.md`. Reasoning: OAAS's own design already makes layout *data* (not pixels) the source of truth, so the golden artifact should be that data, diffed exactly and deterministically. A secondary deterministic SVG render (pinned renderer version, pinned fonts, no time/randomness) with a DOM/attribute-level diff can catch renderer regressions the data-diff can't see. Pixel diff should be advisory-only at most — the visual-regression-testing literature is consistent that font hinting, anti-aliasing, and platform GPU differences make raw pixel diffing flaky by default, requiring perceptual thresholds or OCR-based masking (Percy, Chromatic) to be usable at all, and even then it answers "something changed" without saying what.

**One cautionary tale:** UML Diagram Interchange (OMG DI, 2006). A complete, OMG-ratified standard for exactly the "preserve layout across tools" problem — and it failed to achieve adoption. As of the (still-cited) retrospective, "the only CASE tool [that] supports this standard is Poseidon for UML" (Jordi Cabot, quoted in [modeling-languages.com, 2010](https://modeling-languages.com/anybody-remembers-uml-diagram-interchange-format/)), and a co-author of the UML spec called it outright bad: "The UML Diagram Interchange std DID suck. It will be replaced" (Ed Seidewitz, same source). It *was* replaced — by OMG's Diagram Definition (DD) spec — which tells you the first standard's failure was a design failure, not a "the problem is unsolvable" failure. Lesson for OAAS: a normative layout schema existing on paper is not sufficient; it has to be simple enough, and low-friction enough for implementers, that tools actually bother.

**One success story:** BPMN 2.0 Diagram Interchange (BPMNDI), despite an ugly gestation (see per-source findings below — Bruce Silver's 2009 critique that the diagram-interchange package was defined in a form "not usable by XML tools"), ended up working. OMG's own Model Interchange Working Group (MIWG) ran live, cross-vendor interoperability demonstrations — models built collaboratively across ~8 different vendor tools (Signavio, Camunda, ARIS, Bizagi, Trisotech, and others), imported/exported/round-tripped, with diagrams (not just semantics) surviving the round trip ([bpmn-miwg/bpmn-miwg-test-suite](https://github.com/bpmn-miwg/bpmn-miwg-test-suite); [ACM: "BPMN Model Interchange: The Quest for Interoperability," 2016](https://dl.acm.org/doi/10.1145/2882879.2882886)). The mechanism that made it work, structurally: BPMNDI is *not* a separate file or a separate coordinate space guessed at by convention — it's a distinct XML sub-tree, in the *same document*, whose every shape/edge/label carries an explicit `bpmnElement` reference (a QName pointing at the semantic element's ID) back into the process model. Layout and semantics are separable (different sub-trees, independently processable) but never *decoupled* (every layout object is anchored to a semantic ID, so there is no positional/ordinal coupling to break). Lesson for OAAS: embed layout in the same document, addressed by stable ID, not by position/order, and not as a sidecar file that can drift.

## Per-source findings

### 1. BPMN Diagram Interchange (BPMN 1.x → 2.0)

**Claim under test:** "BPMN 1.x lost diagram layout at interchange boundaries and BPMN 2.0 added the DI sub-spec to fix it."

**Verdict: directionally true, but the precise framing needs correction.** BPMN 1.x did not "lose" layout at interchange boundaries so much as it *never had a standardized interchange format at all* — semantics or layout. There was no BPMN 1.x XML interchange schema; the closest thing to cross-tool portability was tool vendors (ITP Commerce, Fujitsu, Global360, eClarus, TIBCO, BizAgi, Lombardi) piggybacking on XPDL 2.1, an unrelated WfMC standard, "tweaked... using XSLT" per-vendor ([Trisotech, BPMN Introduction and History](https://www.trisotech.com/bpmn-introduction-and-history/); corroborated via search synthesis, not a single quoted primary source — treat the XPDL vendor list as **medium confidence**, single-source). So layout wasn't lost from a shared format; there was no shared format to lose it from. BPMN 2.0 (spec finalized Jan 2011, per OMG's own publication date; ISO/IEC 19510 in 2013) is what introduced the *first* standardized XML interchange for BPMN — for both process semantics and, via a dedicated sub-spec, diagram layout.

**What BPMNDI actually standardizes**, confirmed against the schema itself (via [bpmn-io/bpmn-moddle's mirror of the OMG-published XSDs](https://github.com/bpmn-io/bpmn-moddle/blob/main/resources/bpmn/xsd/BPMNDI.xsd), which ship BPMN20.xsd/BPMNDI.xsd/DI.xsd/DC.xsd copied from the official OMG spec package — this is a faithful mirror, not a reinvention):

- `BPMNDiagram` → contains one `BPMNPlane` + zero or more `BPMNLabelStyle`.
- `BPMNPlane` → the coordinate space; carries `bpmnElement` (a QName reference into the semantic process model — e.g. the `Process` or `Collaboration` this plane visualizes).
- `BPMNShape` (extends the generic `di:LabeledShape`) → carries `bpmnElement` (reference to the semantic element being drawn), a `dc:Bounds` (`x, y, width, height`), an optional `BPMNLabel`, and BPMN-specific booleans: `isHorizontal` (pool/lane orientation), **`isExpanded`** (subprocess collapsed/expanded — direct precedent for "collapse state"), `isMarkerVisible`, `isMessageVisible`.
- `BPMNEdge` (extends `di:LabeledEdge`) → carries `bpmnElement`, `sourceElement`, `targetElement`, an ordered list of `di:waypoint` (each a `dc:Point{x,y}` — the polyline route, source to target), and an optional `BPMNLabel`.
- `BPMNLabel` → its own `dc:Bounds`, **independent of** the shape/edge it labels. Labels are first-class positioned objects, not derived.
- `BPMNLabelStyle` → a `dc:Font` (shared styling, referenced by ID from labels — style/geometry separation).

Critically, `dc:Bounds`/`dc:Point`/`dc:Font` come from a *shared* "Diagram Common" (DC) package, and `di:LabeledShape`/`di:LabeledEdge`/`di:Plane` come from a shared "Diagram Interchange" (DI) package — both under the `http://www.omg.org/spec/DD/20100524/*` namespace, i.e., BPMN's diagram model is a specialization of OMG's *general-purpose* diagram interchange metamodel (the very "Diagram Definition" spec that superseded UML DI — see §2). This is direct evidence that a well-factored generic layout metamodel (geometry + labels + edges, abstracted from any one notation) is reusable across notations — relevant if OAAS wants its layout schema to serve multiple node "kinds" without redefining geometry semantics per kind.

**The messy gestation (the actual "cautionary" texture inside the success story):** Bruce Silver's 2009 critique, written during BPMN 2.0's development (pre-final), argued the diagram-interchange package was defined "in a format usable by [XMI], [not] usable by XML tools," meaning implementers couldn't use ordinary XML Schema tooling (validators, XSLT) against it without extra work; he demonstrated a fix was trivial by hand-writing a working `BpmnDi.xsd` "in a few hours" ([BPMInstitute.org, "BPMS Watch: The DI Mess," Bruce Silver](https://www.bpminstitute.org/resources/articles/bpms-watch-di-mess/); mirrored analysis at [InformationWeek](https://www.informationweek.com/it-sectors/bpmn-2-0-and-the-diagram-interchange-mess)). By the time BPMN 2.0 was finalized (2011), OMG did ship normative XSDs (confirmed: the bpmn-io mirror above is XSD, not XMI/MOF-only) — so the complaint was resolved in the final spec, but it's a documented instance of "we defined the layout metamodel in the wrong artifact type for its target audience (tool implementers using ordinary XML tooling)" as a design mistake to avoid. **Lesson for OAAS:** whatever `spec/visual.md` normatively defines, define it in the same artifact class the rest of the OAAS grammar is defined in (not a foreign metamodeling formalism) — don't repeat BPMN's early mistake of separating the "how do I validate this" tooling story from the main spec's tooling story.

**The eventual payoff:** OMG's Model Interchange Working Group (MIWG) built a public test suite and ran live cross-vendor interoperability demos; ARIS was cited as one of only three tools to pass round-tripping across all three MIWG result groups ([bpmn-miwg/bpmn-miwg-test-suite](https://github.com/bpmn-miwg/bpmn-miwg-test-suite); [omgwiki.org/bpmn-miwg](https://www.omgwiki.org/bpmn-miwg/); academic treatment: [ACM DL, 2016](https://dl.acm.org/doi/10.1145/2882879.2882886)). Today, BPMN 2.0 files with BPMNDI move between Camunda, Signavio, Bizagi, bpmn.io, ARIS, and Trisotech with the diagram intact — this is corroborated by multiple vendor docs (Signavio, Bizagi import docs) but I did not independently verify a recent (2025-2026) round-trip myself; treat "works today across all listed vendors" as **medium confidence**, vendor-marketing-adjacent sourcing.

### 2. UML/XMI Diagram Interchange (OMG DI) — scope and adoption reality

**Scope**, per OMG's own spec document ([omg.org/spec/UMLDI/1.0/PDF](https://www.omg.org/spec/UMLDI/1.0/PDF), fetched directly): DI defines a coordinate/positioning model (shapes, edges, compartments, labels, styling) intended to sit alongside XMI so that *both* model content and layout could interchange between UML CASE tools; it's UML/XMI-generic rather than diagram-type-specific, and (per the fetched excerpt) leans on SVG for the packaged graphical representation. The formal release was 2006.

**Adoption reality — this is the load-bearing finding.** Contemporary commentary (Jordi Cabot, quoted in [modeling-languages.com, Jan 20 2010](https://modeling-languages.com/anybody-remembers-uml-diagram-interchange-format/)): "honestly nobody seems to care about it (maybe I'm wrong but the only CASE tool I remember that supports this standard is Poseidon for UML)." Ed Seidewitz, in the same thread, on why: "The UML Diagram Interchange std DID suck. It will be replaced as part of the new Diagram Definition std." That replacement happened: **OMG's Diagram Definition (DD) specification**, v1.0 Beta1 and v1.1 (dated June 2015 per [omg.org/spec/DD/1.1/PDF](https://www.omg.org/spec/DD/1.1/PDF/)), explicitly "replaces OMG's current Diagram Interchange (DI) specification (formal/2006-04-04)" and provides a more general MOF-based framework (a `DI` package for language-agnostic diagram interchange metamodels, plus a `DG` package mapping those to concrete graphics) "for other modeling language specifications to define their diagrams" against. **This is the same DD package that BPMNDI is built on** (§1) — i.e., DD is the generic layer both UML's and BPMN's diagram formats now specialize, and BPMN's specialization is the one that actually achieved cross-vendor adoption while UML's earlier (pre-DD) attempt did not.

Note on Papyrus UML: the same modeling-languages.com piece notes Papyrus was, by 2010, building support for "DI2" — some later, partial uptake exists, but I did not find evidence of broad UML-tool-ecosystem convergence comparable to BPMN's MIWG story. **Confidence: high** on "UML DI (2006) failed to achieve adoption beyond Poseidon" (multiple independent voices in one primary thread, plus the fact OMG itself replaced the spec); **medium** on DD/DD2's own downstream adoption rate, which I did not separately verify.

### 3. Modern diagrams-as-code: layout as data vs. recomputed, and determinism

| Tool | Layout as data? | Manual position override? | Determinism |
|---|---|---|---|
| **Mermaid** | No — always recomputed from source text on every render. | No general mechanism; users reorder *statements* to nudge output, or (in Architecture diagrams specifically) rely on a `randomize` flag. Two long-standing feature requests for manual layout/position directives (GitHub issues [#270](https://github.com/mermaid-js/mermaid/issues/270), [#2483](https://github.com/mermaid-js/mermaid/issues/2483)) remain unresolved; a maintainer discussion ([mermaid-js/discussions #5088](https://github.com/orgs/mermaid-js/discussions/5088)) indicates no plan to add layout statements. | Deterministic *given the same engine version and same source*: Architecture diagrams default `randomize: false` (seeded start positions) — [mermaid.js.org/syntax/architecture](https://mermaid.js.org/syntax/architecture); the fcose force-layout uses a fixed default seed (`1`) specifically so repeated renders match, which the docs note is required for visual-regression-test stability. Mermaid ships its own visual-regression CI via Argos (screenshot diffing) — [argos-ci.com/customers/mermaid](https://argos-ci.com/customers/mermaid) — i.e., Mermaid itself does **not** rely on layout-as-data; it relies on deterministic *recomputation* plus pixel/perceptual screenshot diffing to catch regressions. |
| **D2 (Terrastruct)** | Partial. Source-level positioning hints exist, but true fixed pixel coordinates are engine-gated. | `near:` keyword works on **all** layout engines for coarse placement (corners/edges of the canvas, or — TALA only — "near" another named shape) — [d2lang.com/tour/positions](https://d2lang.com/tour/positions/). Direct `top`/`left` coordinate-level pinning is explicitly **TALA-only** today ("Works in TALA only. We are working on shims to make this possible in other layout engines" — same page). | Not addressed in D2's own docs in terms of a formal determinism guarantee; TALA is Terrastruct's proprietary engine, Dagre/ELK are the OSS alternatives — determinism would depend on the chosen backend, unverified here. **ASSUMPTION:** D2/TALA layout is deterministic given identical input and engine version — plausible (this is standard for constraint/force-layout solvers run without RNG) but not directly confirmed in fetched docs. |
| **PlantUML** | No — recomputed. | No general per-node override found; PlantUML supports **swapping layout engines** — GraphViz/DOT via subprocess ("Svek"), or **Smetana**, a pure-Java transpiled port of Graphviz/dot's C source, selectable via `!pragma layout smetana` specifically to avoid depending on a native GraphViz binary — [plantuml.com/smetana02](https://plantuml.com/smetana02), [plantuml.com/layout-engines](https://plantuml.com/layout-engines). | Determinism *across engines* is not guaranteed (Smetana "tends to make slightly straighter arrows" than GraphViz — i.e., different engines, different geometry for the same input). Determinism *within* one engine/version was not separately confirmed for PlantUML; see Graphviz findings below, which likely transfer since Svek shells out to real GraphViz. |
| **Graphviz / DOT** | Yes, if you want it to be — but only for a subset of layout engines. | The `pos` attribute is normally **output-only**, but `neato` and `fdp` also accept it as **input** — [graphviz.org/docs/attrs/pos](https://graphviz.org/docs/attrs/pos/). Running `neato -n` (or `-n2`) tells neato "assume nodes are already positioned, use the given `pos`, don't re-layout" — [graphviz.org/docs/layouts/neato](https://graphviz.org/docs/layouts/neato/). Appending `!` to a coordinate (`pos="x,y!"`) pins that node so even a non-`-n` run won't move it. **This mechanism does not exist for `dot`, `circo`, or `twopi`** — hierarchical/radial engines always recompute; only the spring-model engines (`neato`, `fdp`) support fixed/frozen input positions. | Within a single Graphviz version, layout for a given input is effectively deterministic (no RNG in normal operation), **but is not stable across Graphviz versions or fonts**: label sizing depends on font-metrics resolution (via `fontconfig`/LibGD), so "graphviz layout produces different node positions when running the same input... due to edges and nodes being returned in different order" was reported in one thread ([pygraphviz-discuss](https://groups.google.com/g/pygraphviz-discuss/c/fv6chP39lA0); corroborating [networkx-discuss](https://groups.google.com/g/networkx-discuss/c/hdXSeyyUXNo)) — **medium confidence**, forum-sourced, but consistent with the documented font-metric dependency in Graphviz's own [Font FAQ](https://graphviz.org/faq/font/): "if LibGD is not available, graphviz will compute label size using a default system font... the layout may just be slightly incorrect." This is a concrete, named flakiness source (see §4). |
| **Excalidraw** | **Yes, fully** — layout *is* the data model; there is no separate "source" that gets compiled into a diagram. | N/A — every element's position is manually authored/dragged by construction; there's no auto-layout step to override. | Geometry is exactly what's stored (no engine in the loop for structural determinism). Visual *rendering* determinism is explicitly engineered: each element carries a `seed` integer that seeds the `rough.js` hand-drawn-style renderer, "ensuring consistent rendering across sessions" — i.e., the same seed always reproduces the same sketchy stroke jitter, precisely so re-rendering the same file doesn't produce a visually different (if structurally identical) result. |

**Excalidraw JSON scene schema**, confirmed via [docs.excalidraw.com/docs/codebase/json-schema](https://docs.excalidraw.com/docs/codebase/json-schema) plus the actual source ([`appState.ts`](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/appState.ts), [`types.ts`](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/types.ts)):

- Top level: `type: "excalidraw"`, `version`, `source`, `elements[]`, `appState`, `files{}`.
- Per element (common to all types): `id`, `type`, `x`, `y`, `width`, `height`, plus (confirmed via source, not just the docs page, which was itself incomplete) rotation `angle`, an ordering key `index` (see below), `seed`, `groupIds` (grouping), and type-specific fields — `points[]` for lines/arrows (the actual polyline/route, directly analogous to BPMN's `waypoint` list), `startBinding`/`endBinding` (which element an arrow's endpoint is attached to — this is Excalidraw's answer to "how do edges stay attached to nodes when nodes move," relevant to any OAAS edge-waypoint design), and bound-text `containerId` for label-in-shape text.
- `appState`: `scrollX`, `scrollY`, `zoom` (viewport/pan/zoom — **this is the only format in this study that persists viewport as part of the saved file**), `viewBackgroundColor`, `selectedElementIds` (session/selection state, not diagram identity).
- **Z-order**: elements render in array order (later = on top, standard painter's algorithm), *and* Excalidraw additionally maintains an explicit `index` field using **fractional indexing** (lexicographically sortable keys that let an element be inserted "between" two others without renumbering the whole array) specifically to make ordering robust under **collaborative/concurrent editing** — confirmed via the library's own `syncMovedIndices`/`syncInvalidIndices` functions and an open PR adding debug tooling for it ([excalidraw/excalidraw#8235](https://github.com/excalidraw/excalidraw/pull/8235)). This directly answers gap (e) from the wave decomposition: if OAAS's layout format could ever be edited by multiple agents/humans concurrently (plausible, given OAAS's broader agent-oriented design), array-order-as-z-order is a foot-gun; an explicit sortable ordering key is the proven fix.

### 4. Deterministic rendering + golden testing for diagrams

No project studied does **diagram-specific** golden-file testing in a bespoke way beyond general web visual-regression tooling; the closest direct precedent is Mermaid's own CI, and it is screenshot-based, not structural:

- **Mermaid** uses [Argos](https://argos-ci.com/customers/mermaid) (open-source visual-testing tool, screenshot diffing) for PR-level visual regression, plus (per one search-derived, unconfirmed-primary-source claim) Applitools in its release process — **flag this second claim as lower confidence**, I could not independently verify it against Mermaid's own repo docs in this pass.
- **General visual-regression literature** (Percy, Chromatic, Playwright, and multiple 2026 "guide" blog posts — none of these are diagram-specific, all are general web-UI visual testing) converges on the same diagnosis: **text/font rendering is the single largest source of flakiness.** "Browsers rely heavily on the host operating system and... GPU to execute anti-aliasing... A font that renders one sub-pixel bolder after an OS update produces thousands of 'failures,' none of which are product regressions" ([bugbug.io](https://bugbug.io/blog/software-testing/visual-regression-testing/) — secondary/blog-tier source, but the underlying mechanism — OS/GPU-dependent font hinting and anti-aliasing — is well-established and consistent with the Graphviz font-metrics findings in §3). Mitigations reported in industry tooling: containerized/pinned rendering environments to remove OS variance; perceptual/OCR-based diffing (Percy specifically uses OCR to avoid flagging pure text-reflow); tunable pixel-difference thresholds (sub-1% starting point, tuned up from there).
- **Structural/SVG diff as an alternative**: the framing found (via [filediffs.com/svg-compare](https://filediffs.com/svg-compare), a tool-vendor page, so **low-to-medium confidence as a general industry-adoption claim**, but the *argument* it makes is sound and independently corroborated by first-principles reasoning) is that markup-level diffing "can name the exact changed attribute instead of a visual impression" — i.e., it tells you *why*, not just *that*, something changed, and it is immune to font/AA/platform noise by construction, since it never rasterizes.

**Synthesis for OAAS**, combining §3 and §4: since OAAS's own design decision is that native layout is already structured data (not a downstream artifact of some other source), the golden-render loop does not have to choose between "diff the data" and "diff the pixels" as competing primary strategies — it should diff the data as the primary, zero-tolerance gate (this is directly comparable, not to any diagram tool's screenshot-testing setup, but to ordinary AST/config golden-file testing, which is mature, deterministic, and has none of the font/AA flakiness sources at all), and treat a rendered-image comparison as a secondary, advisory smoke test for the deterministic *renderer* itself (pin its version, pin fonts, run in one controlled environment — exactly the mitigations the visual-regression literature recommends when pixel diffing can't be avoided).

## Concrete recommendations for `spec/visual.md`

1. **Embed, don't side-car.** Follow BPMNDI's structural pattern, not Structurizr's: keep layout-as-data in the *same* OAAS document as the semantic graph (as a distinct, separately-processable sub-tree/section), with every layout object carrying an explicit reference to the semantic element's stable ID — never a positional/ordinal reference. Structurizr's split-file model (`workspace.dsl` + `workspace.json`) is workable but has a documented sharp edge: pushing the DSL and the layout JSON out of sync requires an explicit `-merge false` escape hatch to force one to win, which is exactly the kind of two-artifact drift OAAS's "identity projection is total" contract is designed to prevent. Single-document embedding removes the drift vector entirely.

2. **Required fields (per node):** `x, y, width, height` (or equivalent bounding geometry) keyed by the node's OAAS ID; `collapsed: bool` for any composite/container node kind (direct BPMN `isExpanded` precedent) — do not make this a client-side/rendering-only convention, make it normative data, since collapse state changes what's semantically "visible" in a rendered diagram and therefore is part of what "total preservation" must cover.

3. **Required fields (per edge):** an ordered waypoint list (not a derived spline) — even if OAAS's default renderer draws orthogonal or curved routes, the *control points* must be stored, exactly as BPMN and Excalidraw both do, so a re-render without a layout engine in the loop reproduces the same route. Do not rely on a "recompute the route from source+target" strategy as the default (that's the Mermaid model, and Mermaid explicitly cannot do manual layout as a result — this is precisely the capability OAAS's design intends to keep that Mermaid gave up).

4. **Labels are independent objects, not derived positions.** Give every label its own bounding geometry, referencing its owner (node or edge) by ID, exactly as `BPMNLabel` does. This is cheap to add now and expensive to retrofit (BPMN's late convergence on this exact point is telling).

5. **Z-order: prefer an explicit sortable key over implicit document order.** If OAAS's layout section is ever hand-edited, diffed, or concurrently edited by agents, array-order-as-z-order will silently reorder on any insertion/deletion. Excalidraw's fractional-indexing `index` field is the concrete, working precedent; a simpler integer z-index with sparse gaps (classic "leave room to insert between 10 and 20") achieves the same property with less machinery, and would be adequate unless OAAS specifically needs conflict-free concurrent insertion (CRDT-adjacent — likely overkill for v1, but name it as the reason to revisit if agent-collaborative editing becomes real).

6. **Viewport is optional and non-normative.** If OAAS wants to persist a default pan/zoom for human convenience (Excalidraw's `scrollX/scrollY/zoom` precedent), store it, but explicitly exclude it from the golden-render diff / conformance gate — it's session ergonomics, not diagram identity. Say this explicitly in `spec/visual.md` so implementers don't accidentally treat it as normative and start failing conformance on harmless viewport differences.

7. **Golden-render conformance: structural diff on the layout data is the primary, zero-tolerance gate (confirms the `zero-diff-gate` invariant already stubbed in `improvable/render-verify/SKILL.md`).** Round-trip check (serialize → parse → re-render → diff must be zero, also already stubbed) should diff the *parsed layout-as-data structure*, field by field, not a rendered artifact — this sidesteps every flakiness source found in §4 (fonts, anti-aliasing, GPU/platform, renderer-version drift) because it never rasterizes. Reserve a deterministic SVG/DOM structural diff (pinned renderer version, pinned font set, single controlled environment — the exact mitigations the visual-regression-testing literature converges on) as a **secondary, advisory** check specifically to catch bugs in the renderer itself (i.e., cases where the data is byte-identical but the renderer draws it differently — a data diff can't catch that class of bug, only a render diff can). Never gate CI on raw pixel diff; if a perceptual/pixel check is wanted at all, treat it the way Percy/Chromatic do — thresholded, OCR/perceptually-aware, non-blocking.

8. **Define the layout metamodel in the same artifact class as the rest of the OAAS grammar.** Avoid BPMN's early mistake (defining DI in a metamodeling formalism, XMI/MOF, that ordinary XML tooling couldn't consume directly, per Bruce Silver's 2009 critique) — whatever format `grammar/` already uses for the semantic grammar, `spec/visual.md`'s layout schema should be expressible and validatable in that *same* toolchain, not a separate one bolted on for diagrams only.

9. **Reuse a generic geometry substrate if OAAS ever needs more than one visual notation.** BPMN's DI/DC packages are themselves specializations of a generic, notation-agnostic diagram metamodel (now OMG's DD spec) — bounds, points, labels, styles factored out from anything BPMN-specific. If OAAS's node "kinds" (per the profiles/domain structure already in this repo — crypto, agent, ml) end up wanting different visual conventions, factor the shared geometry primitives (bounds, waypoint, label-bounds, collapse, z-order) once, and let kind-specific rendering hints (BPMN's `isHorizontal`/`participantBandKind` are the precedent for "notation-specific accident, not core geometry") extend rather than fork the base schema.

## Assumptions and unresolved items (explicitly flagged, not silently resolved)

- ASSUMPTION: "BPMN 1.x lost diagram layout at interchange boundaries" as literally stated in the research prompt overstates what the evidence shows — the better-supported claim is "BPMN 1.x had no standardized interchange format (semantic or visual) at all," making layout loss a symptom of that absence rather than a specific regression. Recommend `spec/visual.md` (or its accompanying rationale doc) use the corrected framing if it cites BPMN history.
- ASSUMPTION: D2/TALA layout is deterministic given identical input and pinned engine version — plausible by the general nature of constraint/force-directed solvers run without RNG, but not directly confirmed in D2's own docs during this research pass.
- ASSUMPTION: Structurizr's `workspace.json` persists edge waypoints, label anchors, and z-order in addition to node `x,y` — only node-position persistence was directly confirmed; the rest is inferred from "general layout persistence" language in Structurizr's own docs, not independently verified field-by-field.
- ASSUMPTION: Mermaid's use of Applitools in its release process, alongside Argos for PR-level checks — this surfaced only via a synthesized search summary, not a directly fetched/quoted primary source; treat as unconfirmed until checked against Mermaid's own CI config.
- Not investigated (out of scope for this pass, flag for a future unknown if it becomes decision-relevant): whether any of these formats define a normative **coordinate-system convention** (e.g., top-left origin, Y-axis direction, units — px vs. pt vs. abstract grid units) — this matters for cross-tool interchange (BPMN DI, for instance, is silent on this in the fetched excerpts) and OAAS's `spec/visual.md` should decide it explicitly rather than leave it to renderer convention.
